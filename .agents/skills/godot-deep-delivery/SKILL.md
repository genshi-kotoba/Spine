# Godot Deep Delivery

这是对 `docs/agent-guides` 中 DSH 版 deep-delivery 的 Codex 适配。它只描述可在 Codex 中实际执行的检查，不假设 DSH 插件、Windows 路径或不存在的工具。

## 执行规则

1. **先读后问**：先读仓库规则、目标分支、相关场景/脚本、文档和测试。答案已经在本地时不要把查找工作交给用户。
2. **改前复述**：说明目标、范围、基线、验收标准和不在范围内的内容。对 WIP 明确保留“非完成品”状态。
3. **编辑后重读**：重新打开每个改动文件，确认实际内容与目标一致；不要只信工具成功回执。
4. **自己验证**：根据风险执行最小但真实的检查；失败要诊断并尝试替代路径后再升级。

## 验证矩阵

- **静态**：`git diff --check`；Godot 语法/项目检查（例如 `godot --headless --path Spine --editor --quit` 或项目提供的 check 命令）。
- **结构**：场景文件能加载，资源路径存在，新增脚本/UID/输入动作与引用一致。
- **语义**：针对改动的状态机、交互、边界和失败路径做最小断言；不能只数文件或节点。
- **运行时**：优先使用 Godot MCP 的场景树、日志、属性和截图；未执行时明确写“未验证”。
- **负向/碰撞**：检查重复 UID、失效 NodePath、同名资源、非法输入、WIP 已知问题和导入缓存污染。
- **可重复/回滚**：记录重跑是否幂等，以及 Git/`.bak`/存档备份回滚路径。

## 外部仓库与资源

记录来源 URL、分支/ref、commit、PR 状态和许可。下载或引入资源时核对文件魔数/大小、导入文件和 `CREDITS.md`；不因为“看起来存在”就宣称可用。

## 并行交付

分发前为每个流写清稳定 ID、base revision、唯一写入范围、冲突域、验收命令和交付物。最多两个子代理；主代理负责整合和最终复核。中断遵循“续跑原流 → 一次重建 → 如实报告失败”的顺序。

## 交付记录

涉及场景结构、接口、存档、skill 或工作流时，在 `docs/` 下留下简短迁移记录：来源、旧→新映射、验证结果、未验证项和回滚命令。
